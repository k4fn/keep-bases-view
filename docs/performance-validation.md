# パフォーマンス最適化の検証

## 自動検証

`npm ci` 後、`npm test` と `npm run check` を実行する。

Node.js のテストと jsdom で、以下を検証する。

- 厳密プレフィックスと Pinned → Others の依存関係。
- 読み込み失敗のカード単位の隔離と、失敗結果をカードキャッシュに残さないこと。
- 計測済みカードの位置・高さの保持と、10,000 件を超える場合のキャッシュ削除。
- ウォーム復元時に追加のファイル読み込みを行わないこと。
- レイアウトエポック変更後の非同期結果の破棄。
- 画像プローブの Promise 共有、同時実行数 8、失敗 TTL と再試行。
- 画像の自然な縦横比の予約と、失敗画像の欠損表示。
- 画像ファイルの create / modify / delete / rename と CSS 変更による再描画。
- スクロール中のクリック・コンテキストメニューと、停止後の静止カーソル下の操作ボタン復帰。

jsdom はブラウザーのレイアウトを計算しない。テストでは高さとセクション位置を模擬しているため、実際の画像比率・カードのピクセル位置・フレーム所要時間を保証する実機検証とは区別する。

## 計測ログ

プラグイン設定の `Enable performance logging` を有効にすると、開発者コンソールに以下を出力する。

| ログ | 内容 |
| --- | --- |
| `firstVisible` | 初期化から最初の表示までの時間とレイアウト回数 |
| `measureBatch` | 最大 40 枚のバッチ所要時間・件数・レイアウト回数 |
| `scrollRestore` | 復元所要時間・復元先・レイアウト回数 |
| `virtualWindow` | フレーム所要時間・平均・最大・レイアウト回数 |
| `resizeLayout` | リサイズ所要時間 |

各ログにはマウント数とコンテナー配下の DOM 要素数も含める。DOM 数の集計とコンソール出力には負荷があるため、体感の確認時にはログを無効にする。

## 実機で残る検証

この実装作業では Obsidian 実機での変更前ベースライン採取と変更後の定量比較は実施していない。計画の目標値（ウォーム復元 32 ms、コールドで 1,000 / 5,000 枚先への到達時間）は未判定。

同一 Vault・同一画面幅・同一テーマで変更前後を比較する。テキストのみのデータセットと、カバー画像・縦長/横長の本文画像・外部画像・無応答画像・欠損画像・`.base`・読み込み失敗を混ぜたデータセットを用いる。カード数は 1,000 / 5,000 / 10,000 超を用意する。

1. 初期表示、深い位置への移動、カードを開いて戻る操作について、コールドとウォームで上記ログを採取する。
2. 静止カーソルのまま高速スクロールし、マウント数・DOM 数・フレーム時間を比較する。
3. 同一レンダー中の確定済みカードの列・Y 座標が、後続計測・画像読み込み・失敗 TTL 経過で変わらないことを確認する。
4. 本文画像が自然な縦横比で表示され、`.base` の遅延読み込みでカードやタグ位置が変わらないことを確認する。
5. 画像の追加・更新・削除・リネーム、ノートや表示プロパティの編集、テーマ変更、連続リサイズを確認する。
6. スクロール中と停止直後のクリック・右クリック、停止後にマウスを動かさない場合のボタン復帰を確認する。

失敗画像は 60 秒間保持し、表示中の高さは変更しない。TTL 経過後は次回のデータ更新・再表示・レイアウト設定変更で再試行する。
